# Method cards: per layer, "how it works, what to change for a new court, where people have tripped"

Who they are for: people or models adding a new court, a new citation form (a new regex family) or a new jurisdiction to this pipeline.
Purpose: instead of rereading the 150 KB specification and the 157 KB PROBLEMS, read the card for the relevant layer first, then follow the card's pointers to the originals.

## How to read them

| What you want to do | Read first |
|---|---|
| Add a new court (run the whole line) | `00_new_court_playbook.md` |
| Citations are not extracted / a new regex family is needed | `01_extraction.md` |
| Jurisdiction not resolved, homograph abbreviations, non-cases taken as citations, case names cut wrong | `02_classification.md` |
| Problems with counts, keys, case-name voting | `03_merging.md` |
| One case split apart or different cases merged, wrong DD, place of origin | `04_adjudication.md` |
| Threshold, edge files, the DD definition | `05_selection_and_edges.md` |
| Adding rows to a decision table | `06_decision_tables.md` |
| How to verify nothing broke after a change | `07_verification_gates.md` |
| Whether someone has hit a given pitfall before | `08_pitfalls_by_layer.md` |

## Card format (every card follows this order)

1. What the layer does, inputs and outputs
2. **What to change / what not to change when adding a court**
3. How to verify
4. Known pitfalls (with PROBLEMS numbers and status)
5. Sources (specification sections, code locations, PROBLEMS numbers)

## Reliability (read this first)

- Items marked **[verified]** I checked against the code or the actual files (date at the end of each card).
- Items marked **[per spec]** come from the technical specification v1.7 or the PROBLEMS text; entries the specification itself marks "pending review" were not re-verified.
- Items marked **[unverified]** were not checked against the code and must not be used as a basis for implementation (constraint nine).
- The status after a PROBLEMS number is the ledger status on 2026-10-03. Statuses change; before acting, go by the text of `PROBLEMS.md`.

## The nine inviolable constraints (if any plan conflicts with them, change the plan, not the constraint)

1. Fix a problem in the layer that produces it; no bypass lists downstream.
2. The extraction layer uses no fixed list of abbreviations, only structural shapes; table lookups belong to the classification layer.
3. Do not read keywords from surrounding text to decide a jurisdiction.
4. No evidence means `UNSUPPORTED`: no default values, and no `inferred` label as a free pass for guesses.
5. Never delete rows, only flag them (`rejected_reason`, `kept`, etc.).
6. Layers are one-directional and each runs once; downstream may overrule an upstream conclusion but never edits upstream files.
7. A decision table's key must be a fact printed in the judgment, not a key generated by the pipeline.
8. Every decision-table row must carry `source` and `source_locator`; determinations must not be written into code.
9. Unverified numbers and quotations must not be used as a basis.

See spec §2.

## Maintenance

- These cards are human judgement; like `decisions/` they are committed to git, not regenerated on each pipeline run.
- When you change a layer's rules or tables, update the matching card in the same commit.
- The cards are indexed for method search: `python tools/foundation/index_methods.py`; search with `query.py --collection methods`.
